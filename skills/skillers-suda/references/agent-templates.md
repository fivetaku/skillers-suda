# 에이전트 템플릿 가이드

skillers-suda가 에이전트 컴포넌트(`.claude/agents/{name}.md`)를 만들 때 쓰는 구조와 품질 기준.

에이전트 본문은 **브리프**다. 서브에이전트는 메인 대화의 맥락을 모른 채 이 파일과 호출 프롬프트만 받고 시작하므로, "누구인가"보다 "무엇을, 어디까지, 언제 멈추고, 무엇을 돌려주는가"가 결과를 가른다. 성격 형용사나 "당신은 ~를 봐왔습니다" 같은 경력 서술은 출력 품질을 안정적으로 바꾸지 못하고 토큰만 쓴다.

## 1. 에이전트 파일 표준 구조

```markdown
---
name: {agent-name}
description: {무엇을 하는지 한 문장}. Use when {메인 에이전트가 이 에이전트에 일을 넘겨야 하는 상황}.
tools: {필요한 도구만 — 예: Read, Grep, Glob}
model: inherit
---

## 목표
{이 에이전트가 끝냈을 때 세상에 무엇이 달라져 있어야 하는지 1-2문장}

## 입력
- {호출 프롬프트로 받는 것 — 파일 경로, 대상 범위, 기준 등}
- {입력이 빠졌을 때의 처리 — 추측하지 않고 반환 형식의 `blocked`로 돌려준다 등}

## 도구 사용
- {도구별로 언제 쓰는지. 예: Grep으로 후보를 좁힌 뒤 Read로 확인한다}

## 쓰기 범위
- 쓸 수 있는 곳: {경로/파일 패턴 — 읽기 전용이면 "없음"}
- 건드리지 않는 곳: {예: 설정 파일, 다른 스킬 디렉토리, git 커밋}

## 작업 순서
1. {단계 — 왜 이 순서인지 짧게}
2. ...

## 종료 조건
- 완료: {측정 가능한 조건 — 예: 대상 파일 전부 검사, 각 항목에 판정 1개}
- 중단: {더 진행하면 안 되는 조건 — 예: 입력 파일 없음, 쓰기 범위 밖 수정 필요}

## 반환 형식
{메인 에이전트가 그대로 파싱·종합할 수 있는 형식}

```
status: done | blocked
summary: {한 줄}
findings:
  - {항목}: {판정} — {근거 파일:줄}
next: {메인이 할 다음 행동 하나, 없으면 생략}
```
```

### 섹션별 필수 여부

| 섹션 | 필수 | 이유 |
|------|------|------|
| 목표 | **필수** | 무엇을 위해 일하는지 모르면 범위가 흐려진다 |
| 입력 | **필수** | 서브에이전트는 메인 대화를 보지 못한다 |
| 도구 사용 | 권장 | 도구가 2개 이상이면 쓰임새를 적는다 |
| 쓰기 범위 | **필수** | 범위 밖 수정은 되돌리기 어렵다. 읽기 전용이면 "없음"이라고 쓴다 |
| 작업 순서 | 선택 | 다단계 작업에만 |
| 종료 조건 | **필수** | 없으면 언제 멈출지 몰라 과잉 작업하거나 일찍 끝낸다 |
| 반환 형식 | **필수** | 메인이 여러 에이전트 결과를 종합하려면 형식이 같아야 한다 |
| 페르소나·말투 | 선택 | 사용자에게 직접 보이는 문체가 중요할 때만 한두 줄. 결과 품질 장치로 쓰지 않는다 |

### Frontmatter

Claude Code가 읽는 필드만 쓴다.

| 필드 | 필수 | 설명 |
|------|------|------|
| `name` | **필수** | 파일명(확장자 제외)과 같게 |
| `description` | **필수** | 무엇을 하는지 + 언제 넘기는지. 메인 에이전트가 위임 여부를 이것으로 판단한다 |
| `tools` | 권장 | 생략하면 모든 도구를 상속한다. 필요한 것만 쉼표로 나열 |
| `model` | 선택 | 기본은 `inherit`(세션 모델 상속). 사용자가 고른 모델이 있을 때만 바꾼다 |

`vibe`, `source`, `recommended-for`, `team-compatible` 같은 필드는 Claude Code가 읽지 않으므로 넣지 않는다.

## 2. 좋은 에이전트의 특성

| 항목 | 기준 |
|------|------|
| description | 무엇을 하는지 + 언제 넘기는지 (키워드 나열만으로는 부족) |
| 목표 | 하나의 결과에 집중 — "뭐든지 해주는" 에이전트 금지 |
| 쓰기 범위 | 경로 수준으로 명시 |
| 종료 조건 | 완료·중단 조건 둘 다 |
| 반환 형식 | 고정된 키, 근거 위치 포함 |
| 도구 | 필요한 도구만 최소한으로 |
| 분량 | 짧을수록 좋다. 대개 50-150줄이면 충분하다 |

### 품질 등급

| Level | 요건 | 용도 |
|-------|------|------|
| **L1 (Basic)** | name + description + 목표 + 반환 형식 | 단발 위임 |
| **L2 (Team-ready)** | L1 + 입력 + 쓰기 범위 + 종료 조건 | 여러 에이전트를 병렬로 돌리고 결과를 종합할 때 |
| **L3 (Expert)** | L2 + 작업 순서 + 도메인 references | 전문 도메인 에이전트 |

skillers-suda는 기본적으로 **L2 이상**을 생성한다. `scripts/verify_agent.py`가 이 섹션들을 검사한다.

## 3. 도구 배정 가이드라인

| 에이전트 유형 | 권장 도구 |
|--------------|-----------|
| 분석/리서치 | Read, Grep, Glob, WebSearch, WebFetch |
| 코드 작성/수정 | Read, Write, Edit, Grep, Glob, Bash |
| 리뷰/검증 | Read, Grep, Glob, Bash |
| 오케스트레이션 | Read, Write, Agent, Bash |

## 4. Description 작성 (에이전트용)

- BAD: `"코드 리뷰 에이전트"` — 무엇을 하는지도, 언제 넘기는지도 없다
- BAD: `"코드 리뷰, 코드 검토, 코드 봐줘, review code"` — 키워드뿐
- GOOD: `"변경된 파일의 보안 취약점과 성능 병목을 찾아 파일:줄 근거와 함께 보고한다. Use when a diff or PR needs a focused review before merge."`

## 5. 안티패턴

- 역할이 모호한 에이전트 ("뭐든지 해주는 에이전트")
- 도구 과다 배정 (All tools → 필요한 것만)
- 쓰기 범위·종료 조건 없이 자유 행동 허용
- 반환 형식이 없어 메인이 결과를 다시 해석해야 함
- 성격 형용사·경력 서술·말투 예시로 본문을 채움
- model을 불필요하게 고정 (`inherit` 권장)
